# Mathematics, Signal Processing, and Statistics

Every sensor reading covered earlier in this guide arrives as a raw number, on whatever scale the hardware happens to produce it, and a raw number is rarely the number actually needed. Turning a 0–4095 ADC reading into a 0–255 PWM value, deciding how often it is even valid to take a new reading, and boiling a whole log of readings down into a single trustworthy minimum, maximum, or average are not incidental chores; they are where real, if simple, mathematics sits underneath code already written and mostly taken for granted. This section is about recognising that mathematics when it is present, so it can be reasoned about instead of simply trusting that `map()` or an average "just works."

**`map()` is a linear equation.** A typical worked example is `map(potValue, 0, 4095, 0, 255)`, taking the potentiometer's raw ADC reading (which ranges 0–4095 on the ESP32's 12-bit ADC) and linearly rescaling it into the 0–255 range `analogWrite()` expects for PWM. "Linear" here means the relationship is a straight line: an input exactly in the middle of its range always produces an output exactly in the middle of *its* range, with no curve or bending. In general form:

```
output = (input − inMin) × (outMax − outMin) / (inMax − inMin) + outMin
```

Every term in this formula does a specific job: `(input − inMin)` measures how far into its input range the value currently sits; dividing by `(inMax − inMin)` turns that into a *proportion* (a fraction between 0 and 1); multiplying by `(outMax − outMin)` rescales that same proportion into the output range's size; and adding `outMin` shifts it to start at the right place. This is real algebra directly embedded in a function already called many times, and the *same* general form applies on an Arduino Uno's 10-bit ADC too, with `inMax` changed from 4095 to 1023 to match that chip's actual ADC resolution. The formula never changes; only the numbers describing the specific hardware's range do.

**What "sampling" means.** A real-world physical quantity like temperature does not change in sudden steps: it varies continuously, every instant. A digital sensor, however, can only ever report its value at specific, discrete moments in time; each individual reading is called a "sample." The gap between samples matters: the DHT22's roughly 2-second minimum interval between reliable readings is a direct, concrete example of a sensor's sampling rate being limited by the hardware itself. Reading it faster than that produces invalid or repeated data instead of more information. This idea scales up dramatically in other contexts: an oscilloscope (see the Laboratory Test Equipment section above) is itself just a very fast sampler, taking millions of voltage samples per second so a waveform looks smooth and continuous rather than obviously stepped.

**Why statistics need correct, correctly-typed data underneath them.** Basic statistics (minimum, maximum, and average) are commonly computed over logs of readings. These numbers are simple to calculate, but they are only *meaningful* if every value feeding into them is correctly labelled and correctly typed. A single reading accidentally stored in the wrong type (e.g. a fractional sensor value truncated by being stored in an `int` instead of a `float`), or a sentinel/error value accidentally included in the average instead of being filtered out first, will silently produce a statistic that still looks like a perfectly ordinary number. It will just be wrong. This ties directly back to why type correctness matters for reasons beyond "the code compiles and runs," and it applies with equal force on any microcontroller family: a truncated float is a truncated float whether the chip underneath is an ESP32 or a PIC.
