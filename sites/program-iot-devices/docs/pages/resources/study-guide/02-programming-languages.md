# Language Used to Program IoT Devices

Every sensor reading, calculation, and wireless message described later in this guide must be expressed as code running on real hardware. Understanding that language, and why it takes the shape it does, is a necessary foundation. An IoT device is not a general-purpose computer running a general-purpose language by accident: its language and conventions exist because the device runs indefinitely without an operating system to fall back on, and has a small, fixed amount of memory that cannot be expanded. This section covers that language: what it is, why its structure differs from a language written for a desktop, and how the same core ideas appear across different microcontroller toolchains.

This guide works primarily with the **ESP32** family of boards, programmed in the **Arduino framework, which is C/C++**, the same language framework used across many other microcontroller boards (ESP8266, STM32, and others). Understanding why this language is used, rather than simply naming it, is the more useful takeaway.

**Why an embedded language looks different from a desktop one.** A desktop C++ program has a `main()` function: it starts, does its work, and exits, handing control back to the operating system. An embedded device never "exits": it is powered on, does its job, and keeps doing it until the power is removed. Arduino's C/C++ framework reflects that reality directly with two functions instead of one:

- **`setup()`** runs exactly once, immediately after power-on or a reset. This is where pin modes are configured (`pinMode()`), communication is started (`Serial.begin()`, `Wire.begin()`), and any sensor library is initialised. Anything that only needs to happen once belongs here.
- **`loop()`** runs continuously for as long as the board has power. This is where sensors are read, conditions evaluated, and actions taken: the device's ongoing behaviour lives here.

**Why data types matter more here than on a PC.** On the ESP32, an `int` occupies 4 bytes and a `double` is a true 8-byte double-precision value (this differs from some smaller AVR-based boards, where a `double` behaves identically to a 4-byte `float`, because the compiler does not implement a separate double-precision path). A desktop application usually has gigabytes of RAM and can treat memory as effectively unlimited; a microcontroller has a small, fixed amount of RAM and flash storage soldered onto the chip, with no way to add more and no virtual memory or swap space to fall back on. Choosing a data type larger than necessary (a `double` where a `float` would do, or an `int` to store a value that only ever ranges 0–255) wastes a limited, non-renewable resource. On a PC, the same waste would likely go unnoticed.

**Direct hardware access.** Functions like `digitalRead()`, `analogRead()`, and `analogWrite()` map directly onto physical microcontroller pins. A general-purpose desktop language has no equivalent concept: there is no "pin 18" for a language like Python running on a laptop to read from.

**IDE note.** The **Arduino IDE** is the most common environment for this workflow, with its Serial Monitor as the default debugging tool. **PlatformIO** is a common alternative for larger, multi-file project structures. Both are ways of writing and uploading the same underlying Arduino C/C++ code, not different languages.

**Beyond the ESP32, the same idea, different toolchains.** The `setup()`/`loop()` pattern is an Arduino-framework convention, not a universal law of embedded programming. The same "run forever, with no OS to return to" reality takes different forms elsewhere:

- **AVR (Arduino Uno):** the same `setup()`/`loop()` Arduino framework runs here too, which is why Uno code and ESP32 code look nearly identical at the sketch level. Underneath, however, the ATmega328P has only 2 KB of RAM and 32 KB of flash, two to three orders of magnitude less than an ESP32, so the "do not waste a `double` where a `float` will do" lesson matters far more here: a handful of oversized variables can exhaust an Uno's RAM and cause silent, hard-to-diagnose crashes.
- **STM32:** typically programmed in bare-metal C/C++ against ST's **HAL** (Hardware Abstraction Library) or the lower-level **CMSIS** layer, rather than the Arduino framework (though an Arduino-compatible core also exists). Instead of `setup()`/`loop()`, a typical STM32 program has an explicit `main()` containing an initialisation block followed by a hand-written `while(1) { ... }` infinite loop: the same "initialise once, then run forever" shape as Arduino, without the framework concealing it.
- **RP2040 (Raspberry Pi Pico):** supports the Arduino framework (so `setup()`/`loop()` works here too), a lower-level C SDK with its own `main()` + `while(true)` loop, and MicroPython. It illustrates that the underlying hardware and the language/framework choice are two separate decisions.
- **PIC:** commonly programmed in C with Microchip's **XC compilers** inside **MPLAB X**, again structured as `main()` with a manual `while(1)` loop, or historically in assembly for the smallest parts. PIC toolchains reinforce fixed-width types (`uint8_t`, `int16_t`) even more strongly than Arduino does, because many PIC parts have only a few hundred bytes of RAM.

The common thread across all five: **whatever the syntax, an embedded program always ends up being "initialise once, then loop forever,"** and data-type discipline matters more than it would on a desktop, to a degree that scales with how little RAM and flash the specific chip has.

**Languages used to program IoT devices.** This guide's own builds use Arduino C/C++, but that is one point on a wider landscape. Different languages suit different layers of an IoT system, from the bare microcontroller up to a Linux-based edge device:

- **C:** the foundation almost every microcontroller toolchain in this guide is ultimately built on (directly, or underneath the Arduino framework's C++). It compiles down to small, predictable, fast machine code with direct hardware access and no hidden runtime overhead, exactly what a chip with kilobytes of RAM needs.
- **C++:** what the Arduino framework actually is (`setup()`/`loop()`, `Serial`, and every other Arduino "function" are really C++ under the hood). It adds object-oriented features (classes, libraries as objects) on top of C, which is why sensor libraries can be used as `dht.readTemperature()` rather than a raw C function call, while still compiling down to the same efficient machine code.
- **MicroPython / CircuitPython:** a stripped-down Python interpreter that runs directly on a microcontroller (supported on the RP2040/Pico, and on many ESP32 boards). It trades some speed and memory efficiency for Python's simpler syntax and interactive REPL, making it popular for fast prototyping and teaching, at the cost of being slower and more memory-hungry than compiled C/C++.
- **Python:** not run on a bare microcontroller at all, but common on Linux-capable IoT devices (a Raspberry Pi, or the Linux side of a hybrid board like the Arduino UNO Q) for higher-level logic: reading data, calling cloud APIs, running a dashboard, while time-critical hardware control is often handed off to a microcontroller.
- **Rust:** a newer, increasingly popular option for embedded work, offering C/C++-level performance and direct hardware access, with compile-time memory-safety guarantees that eliminate entire categories of bugs (buffer overruns, use-after-free) common in hand-written C. Support is growing for the ESP32, STM32, and RP2040, though its ecosystem and tooling remain less mature than C/C++'s.
- **JavaScript:** used on some IoT hardware via runtimes like Espruino (a JavaScript interpreter for microcontrollers) or Node.js-based frameworks like Johnny-Five (running on a host computer and communicating with a microcontroller over a serial link). It appeals to developers already familiar with JavaScript from web development, at a real cost in speed and memory efficiency compared to C/C++.
- **Assembly:** the lowest-level option, writing the chip's own native instructions directly with no compiler in between. Rarely needed on modern microcontrollers with capable C compilers, but still occasionally used for the most timing-critical routines or on the smallest, most memory-constrained parts (some PIC10/12-class chips, for instance).

**Why this guide focuses on C/C++.** Every microcontroller family compared throughout this guide can be programmed in C/C++: it is the language every other option on this list either compiles down to, wraps, or was invented partly to replace. That makes it the most transferable starting point, regardless of which board or language a future project eventually requires.
