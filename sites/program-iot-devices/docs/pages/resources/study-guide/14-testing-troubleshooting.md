# Testing and Troubleshooting
Every section before this one has explained how something is *supposed* to work (a sensor's principle of operation, a resistor's current-limiting role, a Wi-Fi connection's lifecycle). Real hardware does not always cooperate with that theory: wires come loose, sensors occasionally misbehave, and networks drop without warning. This section is about what to do when that happens, not by guessing, but by working through a fault methodically, in an order that gets to the actual cause with the least wasted effort. Debugging at this level often relies entirely on `Serial.println()` output checked in the Arduino IDE's Serial Monitor, without a formal debugging *methodology* ever being named as its own topic, which is itself worth being upfront about.

**A sensible order for troubleshooting an intermittent fault** (one that only appears occasionally rather than every single time, for example, a sensor reading that is occasionally invalid, or a wireless upload that occasionally fails):
1. **Check wiring and power first.** This is both the most common real-world cause of an intermittent fault and the fastest one to rule out: a loose connection or a marginal power supply produces exactly this kind of "sometimes it works" symptom.
2. **Check connectivity and environmental factors second.** For a wireless upload, check the Wi-Fi connection status at the moment of failure; for a sensor, consider timing (was it read too soon after a previous read?) or environmental interference.
3. **Trace with `Serial.print()` third**, once the obvious physical/environmental causes have been ruled out. Printing the actual values the code is working with at each relevant step shows exactly *which* value is wrong and *when* it goes wrong, rather than requiring guesswork.

This order matters because it moves from the simplest, cheapest checks to the more time-consuming ones: there is little point spending twenty minutes tracing through the code's logic if the real problem turns out to be a loose jumper wire.

**A fault category that only exists once a build leaves the simulator.** In the simulator, a circuit either matches its wiring diagram exactly or it does not: there is no such thing as a connection that is "mostly" made. On the physical breadboard, step 1 above (check wiring and power first) covers a genuinely new class of fault that never existed in simulation: a jumper wire that is inserted at a slight angle, a breadboard row with a worn or dirty contact, or a component leg that is not fully seated. These produce exactly the "intermittent, works-sometimes" symptom this section is about, and they are now a real possibility the troubleshooting order has to account for, one it never had to on the simulator alone.

**Logic bug vs. environmental/connectivity issue, and why the distinction changes the fix.** A **logic bug** is a defect in the code's own decision-making or calculations, something that is *always* wrong under the right conditions, and the correct fix is to change the code itself. An **environmental or connectivity issue** (a Wi-Fi connection that occasionally drops, electrical noise occasionally corrupting a sensor reading) is external to the code; the code was never wrong. The *conditions* around it changed. The correct fix here is not to rewrite working logic, but to make the code more resilient to that external reality: exactly what a `maybe_reconnect()`-style pattern does for a dropped Wi-Fi connection, and what a DHT22 `isnan()` check does for an occasional bad sensor reading. Misdiagnosing one as the other wastes real effort: rewriting already-correct logic to chase a connectivity glitch fixes nothing, while wrapping a real logic bug in a retry loop hides the defect instead of correcting it, letting it resurface later.

**Debugging tools change across microcontroller families, even though the methodology above does not.** `Serial.println()` read from a USB-connected terminal is an Arduino-framework convenience available on the ESP32, the Uno, and the RP2040 alike. Professional STM32 and PIC development, by contrast, commonly uses **hardware debugging**: an ST-Link (STM32) or PICkit/ICD (PIC) debug probe connects over a dedicated debug interface (SWD or ICSP) and allows the running program to be paused mid-execution, stepped through line by line, with the exact contents of variables and registers inspected directly, something no amount of `Serial.print()` statements can fully substitute for. The *order of investigation* taught above (wiring/power, then connectivity/environment, then trace the code) stays the same regardless of which of these tools is used; only the mechanics of "trace the code" become more powerful as the tooling does.
