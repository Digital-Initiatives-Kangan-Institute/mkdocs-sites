# Sensors and Wireless Communication

<p align="center"><img src="../../../../assets/study-guide/05-sensors-and-wifi.png" alt="PIR, potentiometer and DHT22 sensors compared by how each converts a physical quantity into a signal, plus the Wi-Fi connection lifecycle from WiFi.begin() through WL_CONNECTED with a non-blocking reconnection loop" width="700"></p>

A microcontroller on its own is deaf, blind, and mute. It can run logic, but it has no way to know anything about the physical world around it, and no way to tell anything outside itself what it found, unless something bridges that gap. **Sensors** are one half of that bridge: hardware that converts a real-world physical quantity (motion, position, temperature, humidity, distance, light) into an electrical signal a microcontroller's pins can read. **Wireless communication** is the other half: it takes what the microcontroller has learned or decided and sends it somewhere else (another device, a phone app, a cloud dashboard) without a physical wire ever having to run there. Neither half is optional in most real IoT systems: a device that senses but cannot communicate is just an instrument sitting in a room; a device that communicates but senses nothing has nothing worth sending. This section covers both halves: three different sensor designs that solve the same "physical quantity to digital signal" problem in different ways, and the Wi-Fi connection lifecycle that solves the "get data somewhere else, reliably, without freezing everything else" problem.

**How each sensor turns a physical quantity into something code can read:**

- **PIR (Passive Infrared) motion sensor:** a purely digital sensor. It contains a pyroelectric element that responds to a *change* in infrared radiation (heat) within its field of view, essentially something warm moving across its detection zone. Internally, that change is converted into a simple digital HIGH or LOW signal, read with a plain `digitalRead()`. There is no "amount" of motion reported, only detected or not detected. This is completely independent of the microcontroller reading it: a PIR outputs the same HIGH/LOW logic pulse whether it is read by an ESP32, an Uno, an STM32, or a PIC. The only thing that changes is whether that pin is a 3.3 V-logic input (ESP32, STM32, RP2040) or a 5 V-logic input (Uno, many PIC parts).
- **Potentiometer:** a purely analogue sensor. Physically turning its shaft moves a wiper across a resistive track, changing the resistance between its terminals. That changing resistance changes the voltage present at the wiper pin (following a voltage-divider relationship), and the microcontroller's onboard **ADC** (Analogue-to-Digital Converter) samples that continuously variable voltage and reports it as a discrete number. This is one of the few places where the *microcontroller*, not the sensor, determines the numbers that appear in code: the ESP32's ADC reports **0–4095** (12-bit), an Arduino Uno's reports **0–1023** (10-bit) for the same physical voltage swing, and an RP2040 also reports 0–4095 (12-bit). The potentiometer itself has not changed between these; only the resolution of the chip digitising it has.
- **DHT22:** a digital sensor with its *own* communication protocol on a single data pin (it is not a simple digital HIGH/LOW like the PIR, nor a simple analogue voltage like the potentiometer; it sends a timed sequence of pulses that a library decodes into temperature and humidity values). Two practical consequences follow directly from this design: readings must be checked with `isnan()`, because the sensor occasionally returns an invalid result if the timing is disrupted; and it can only be read reliably about once every 2 seconds, because the sensor's own internal measurement cycle is slow compared with, say, a potentiometer, which can be read essentially as fast as desired. This timing sensitivity is also why a DHT22 library needs to exist per platform: the bit-banged timing that works on an 8-bit AVR running at 16 MHz needs re-tuning (or a different, interrupt-driven approach) on a 32-bit ESP32 or RP2040 running far faster, even though the sensor's wire protocol itself never changes.

**What changes once these sensors are wired on a real physical breadboard, rather than simulated.** A simulator generally reports a sensor's behaviour as its model defines it. A real PIR, potentiometer, or DHT22 on a real breadboard can behave slightly differently from build to build: a jumper wire that is not fully seated can produce a flickering digital signal on the PIR that looks like phantom motion, a potentiometer's `analogRead()` values can jitter by a few counts even when the shaft is not moving (genuine electrical noise), and a DHT22's `isnan()` check catches real, occasional invalid readings that a simulated version might never produce. None of this changes how the sensor *works*. It is the same physical principle either way, but it is a real difference in what to expect once the same code runs on the real board, on any microcontroller family.

**Wireless communication, the Wi-Fi/ThingSpeak build, mechanism by mechanism:**
`WiFi.begin(ssid, password)` does not connect immediately; it *starts* an asynchronous connection attempt in the background. While this negotiation is happening (authenticating with the access point, then obtaining an IP address via DHCP), the rest of the program is free to keep running; it is not blocked waiting. `WiFi.status()` is polled afterwards, at intervals, to check progress, and only once it returns `WL_CONNECTED` is the device actually able to send or receive data on the network.

A real deployed device needs a **non-blocking reconnection pattern**, commonly a function like `maybe_reconnect()`, which checks `WiFi.status()` against its own `millis()`-based timer rather than sitting inside a blocking `while` loop, because a Wi-Fi connection cannot be assumed permanent once established. Interference, the access point restarting, or simply moving out of range can drop it at any moment, and a real device still has other responsibilities (reading sensors, evaluating alert logic, driving outputs) that must keep running even while it is waiting to reconnect. A blocking reconnection attempt would freeze the *entire* device, including all of those other responsibilities, for as long as reconnection takes, which could be seconds or indefinitely if the network never comes back.

**Wireless is a differentiator between microcontroller families, not just a software detail.** The ESP32's Wi-Fi (and Bluetooth) radio is built into the chip itself, which is why an ESP32-based Wi-Fi build needs no extra hardware. An Arduino Uno and most STM32 and PIC parts have **no radio on-die at all**: a real project on one of those needs an external module (an ESP8266/ESP32 acting as a Wi-Fi co-processor, an add-on Ethernet or LoRa shield, and so on) wired in over SPI, UART, or I²C, with its own separate library and command set. The Raspberry Pi Pico splits the difference: the plain **Pico** has no radio, while the **Pico W** variant adds one. None of this changes the connection *lifecycle* described above (begin, poll status, wait for connected, handle drops without blocking), but it does mean that "does this board have Wi-Fi" is a real hardware question that must be checked on a per-board, sometimes per-variant, basis before assuming a project is possible on a given chip.
